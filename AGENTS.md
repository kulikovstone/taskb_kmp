# Платформы и общий код

Основная разработка ведётся для Desktop; следующая платформа — Android.
iOS и Web пока остаются каркасом на будущее. Сохраняйте их модули, targets и
согласованность общих API, но полноценную реализацию для этих платформ добавляйте
только в рамках отдельной задачи.

Общую логику, MVI, навигацию, модели и переиспользуемый Compose UI размещайте в
`src/commonMain/kotlin`. Общие тесты размещайте в `src/commonTest/kotlin`.
Код, зависящий от платформы, размещайте в соответствующем source set:
`androidMain`, `jvmMain`, `iosMain` или `webMain`; платформенные тесты — например,
в `jvmTest`. В KMP-библиотеках Desktop соответствует target `jvm` и source set `jvmMain`.
У платформенных приложений `:app:desktopApp` и `:app:androidApp` исходники находятся в `src/main`.

В `commonMain` не используйте API Android, Java/JVM, Swing и AWT.
Платформенные различия оформляйте через общие интерфейсы с внедрением реализации
или через `expect`/`actual`, следуя существующему коду.
Для дат используйте подключённый `kotlinx-datetime`, а не `java.time` в общем коде.
Не дублируйте фичи отдельно для Desktop и Android.
Базовый пакет приложения и общих модулей — `com.mkulikov.taskb`.

# Границы модулей

- `:app:shared` объединяет общие фичи, DI и интерфейс приложения; платформенные
  приложения содержат точки входа и платформенную настройку.
- `:core:mvi`, `:core:navigation`, `:core:database` и `:core:utils` — самостоятельные модули
  инфраструктуры. Каталог `core` служит группировкой; общей библиотеки `:core` нет.
- `:feature:<name>` содержит реализацию фичи, а `:feature:<name>:api` — её публичные
  контракты. Зависимости между фичами проводите через `api`, а реализации объединяйте
  в `:app:shared`.
- `:ui` содержит общую тему, палитру, иконки и переиспользуемые компоненты.

Все универсальные утилиты, не привязанные к конкретной фиче, храните в `:core:utils`.
Общие утилиты размещайте в `core/utils/src/commonMain/kotlin`, группируя по назначению,
например `time`. Модуль утилит не должен зависеть от фич и UI; платформенные
реализации утилит размещайте в соответствующих source sets этого модуля.

Общую конфигурацию базы Room храните в `:core:database`; сущности и DAO задач и
настроек находятся в соответствующих API-модулях фич. Открытие базы и выбор пути
хранения зависят от платформы. При изменении схемы сохраняйте историю в
`core/database/schemas` и учитывайте миграции существующих данных.
Сохраняйте имя класса базы и совместимость прежнего Desktop-пути хранения.

Используйте существующие модули Koin и контейнер `AppDependencyGraph` в `:app:shared`.
Жизненный цикл контейнера и базы связан с Compose; учитывайте закрытие ресурсов.

# Цвета интерфейса

Используйте цвета из общей палитры `Palette` в `ui/src/commonMain/kotlin/theme`.
В теме задавайте семантические цвета через `Palette`, а в компонентах и экранах
используйте `TaskBTheme.colors`. Для выбора конкретного цвета, например цвета группы,
обращайтесь к `Palette` напрямую.
Не задавайте произвольные HEX/RGB-значения цветов в теме, экранах и компонентах.

# Иконки интерфейса

Используйте готовые иконки из подключённой библиотеки Material Symbols
(`com.composables.icons.materialsymbols`) через общий объект `TaskBIcons`
в `ui/src/commonMain/kotlin/icon`.
Если нужной иконки нет в `TaskBIcons`, добавьте туда ссылку на иконку из библиотеки.
Не создавайте собственные SVG/PNG, векторные пути или рисунки на Canvas для иконок интерфейса.

# Экраны фич

Каждый экран фичи размещается в папке
`feature/<feature>/src/commonMain/kotlin/screen/<screen_name>/` вместе со своим Store,
состоянием, Intent, reducer и другими классами, относящимися к этому экрану, если они нужны.
Не создавайте папки `mvi` на уровне фичи.
Для тестов конкретного экрана используйте такую же структуру `screen/<screen_name>/`
в соответствующем тестовом source set.
Общий для нескольких экранов код размещайте вне папок отдельных экранов.

# Файлы MVI для экранов

Для экранов с MVI размещайте объявления в отдельных файлах внутри папки экрана:

- `<Screen>State.kt` — состояние экрана, его вычисляемые свойства и связанные с состоянием
  модели, например типы диалогов. Модели диалогов оставляйте в файле состояния.
- `<Screen>Intent.kt` — тип Intent экрана и его варианты.
- `<Screen>Reducer.kt` — тип Message экрана и его варианты вместе с функцией `reduce<Screen>`.
- `<Screen>Store.kt` — реализация Store. Не объявляйте State, Intent, Message или reducer
  в этом же файле.

# Имена интерфейсов и реализаций

Интерфейсы, задающие контракт поведения, называйте с префиксом `I`, например
`IGroupRepository`, `IAppSettings`, `IStore`, `IGroupDao`.
Классы реализаций называйте без префикса `I`. Основная реализация `IGroupRepository`
должна называться `GroupRepository`, без указания технологии хранения в имени.
Для отдельного интерфейса или класса имя файла должно совпадать с именем типа.
Для MVI используйте правила группировки из предыдущего раздела.
Платформенные реализации могут иметь суффиксы `.android.kt` или `.jvm.kt`,
как существующие файлы открытия базы, либо одинаковое имя в разных source sets,
как реализации `TaskBFontFamily.kt`.
Для типов, описывающих варианты данных (`Intent`, `Message`, `Dialog`, маршруты),
префикс `I` не используется.

# Сборка, зависимости и версия

Используйте Gradle Wrapper из корня этого проекта.
Версии библиотек, плагинов и Android SDK задавайте в `gradle/libs.versions.toml`.
Общие настройки KMP-библиотек изменяйте в convention plugins модуля `build-logic`:
`taskb.multiplatform.library` и `taskb.compose.library`.
Не переносите настройки старых JVM-модулей напрямую в общие KMP source sets.

Для обычных библиотечных модулей с Compose используйте `taskb.compose.library`:
он также подключает аннотации Preview в `commonMain` и tooling через `androidRuntimeClasspath`.
У `:app:shared` отдельная конфигурация, включающая iOS frameworks;
в нём зависимости Preview настроены непосредственно в `build.gradle.kts`.
Для превью используйте `androidx.compose.ui.tooling.preview.Preview`.
Примеры превью должны получать тестовые данные без открытия реальной базы приложения.

Версия приложения вычисляется плагином `taskb.versioning` из `version-major.txt`
и истории Git. Меняйте `version-major.txt` только для начала новой базовой серии.
Не задавайте версии вручную в модулях и не редактируйте сгенерированный `AppVersion.kt`.
Команды запуска и упаковки Desktop описаны в `README.md`.

# Проверки изменений

Выбирайте проверки по затронутому коду:

- Тесты изменённого общего модуля: `./gradlew :feature:task:jvmTest`
  (подставьте путь нужного модуля).
- Интеграция приложения, навигация и UI Desktop: `./gradlew :app:shared:jvmTest`.
- Компиляция Desktop: `./gradlew :app:desktopApp:compileKotlin`.
- Сборка Android при изменении общего кода, Android-кода или конфигурации его сборки:
  `./gradlew :app:androidApp:assembleDebug`.
- Тесты логики сборки при её изменении: `./gradlew :build-logic:test`.

Для обычных задач Desktop и Android не требуется полная сборка всех targets,
включая iOS и Web. Изменения только документации не требуют запуска Gradle.
